# T-07: Link expiry (ambiguous → decided)

## Intent
Let creators give a link an optional expiry, per ADR-002, without changing
behaviour for existing links.

## Context
- Requirements: FR-7; Q-6 resolved by ADR-002; A-3 (permanent by default)
- ADR-001 D3 (302, so expiry takes effect immediately)
- Builds on T-06; baseline-greenfield rules still apply to pre-existing tests

## Scope
In scope:
- `POST /api/v1/links` accepts an optional `expires_at` (ISO 8601 with a
  time zone). Rejected with 422 if it has no time zone or is not in the
  future. Stored in UTC.
- Create and details responses include `expires_at` (null when none).
- `GET /{code}` for an expired link → 410 in the standard error shape
  (code `link_expired`); no click recorded
- Details and stats endpoints keep working for expired links
- Migration 0003: nullable `expires_at` column on `links`; existing rows
  NULL (never expire)

Out of scope:
- Changing or removing expiry after creation
- Cleanup or archival of expired links
- A maximum expiry horizon

## Constraints
- Expiry check in the service layer with an injectable clock (as
  StatsService does); expired when now >= expires_at
- The 410 response carries `Cache-Control: no-store`
- Migration uses batch mode (SQLite ALTER TABLE); upgrade and downgrade on
  SQLite and Postgres; existing links survive and stay non-expiring
- Existing tests: if any asserts an exact response body that the new
  `expires_at` field would change, list it in the plan. Do not change it
  without my approval
- If you need to deviate from the approved plan, stop and ask before
  making the change
- Annotated style; standard error shape; no new dependencies

## Acceptance criteria
1. Create without `expires_at` → link never expires; response has
   `expires_at: null`.
2. Create with a future, time-zone-aware `expires_at` → stored in UTC and
   returned.
3. `expires_at` in the past, equal to now, or without a time zone → 422 in
   the standard shape.
4. Redirect before expiry → 302 and one click recorded; at or after expiry
   → 410 `link_expired`, `no-store`, and no click recorded (injected clock,
   including the exact boundary).
5. Details and stats for an expired link → 200, with `expires_at` shown.
6. Migration up/down on SQLite and Postgres; existing links survive with
   `expires_at` NULL and still redirect.
7. All pre-existing tests pass (any exact-body exceptions approved as above);
   the latency test still passes.
8. Unit and integration tests for the above.
