# T-05: Hardening — health, errors, rate limiting, latency

## Intent
Make the service operable and safe to expose: health and readiness probes,
one consistent JSON error shape with no internals leaked, rate limiting on
link creation, and an automated check on redirect latency.

## Context
- Depends on: T-04 (redirect and details routes, LinkNotFoundError handler),
  T-03 (create endpoint, 422/503 handling)
- Requirements: Reliability (health/readiness endpoints; consistent JSON
  errors), Security (rate limiting on creation), Performance (redirect p95
  < 50 ms at the app layer), Privacy (no raw IP addresses stored)
- Plan: docs/plan.md T-05.1–T-05.4, including its known trade-offs

## Scope
In scope:
- T-05.1 `GET /health` → 200 `{"status": "ok"}`, no DB access.
  `GET /ready` → 200 `{"status": "ready"}` if the DB answers a trivial query,
  else 503 in the standard error shape (no driver or connection details)
- T-05.2 One error shape for every error response:
  `{"error": {"code": "<machine_code>", "message": "<human text>"}}`,
  plus an optional `"details"` list for validation errors (field location and
  message only, never the submitted input). Covers: request validation (422),
  unknown routes (404), method not allowed (405), unknown/malformed codes
  (404), code-space exhaustion (503), rate limit (429), readiness failure
  (503), and any unhandled exception (500: generic message, full traceback
  logged server-side, never returned)
- T-05.3 Rate limit on `POST /api/v1/links` only: in-memory, per client IP,
  default 10 requests per 60 s, configurable via settings. Exceeding it →
  429 with a `Retry-After` header. Redirects, details, health and ready are
  not limited
- T-05.4 Redirect latency test: after a warm-up, a few hundred in-process
  `GET /{code}` requests; assert p95 < 50 ms; on failure, print p50/p95/max

Out of scope:
- Analytics and click recording (T-06), expiry (T-07)
- Distributed or shared rate limiting (e.g. Redis), per-user quotas
- Request logging, metrics, tracing, request IDs
- Converting T-03 routes to the Annotated style (separate follow-up)

## Constraints
- Layering per CLAUDE.md. The rate limiter is a FastAPI dependency on the
  create route, not global middleware, so redirects are untouched by design
- `/health` and `/ready` are single-segment paths, so `/{code}` would match
  them if registered first. They must be registered before the redirect
  router, which stays last
- Rate limiter: keyed on `request.client.host`, not on `X-Forwarded-For`
  (spoofable without a trusted proxy). Clock injectable for tests; thread-safe
  (sync endpoints run in a thread pool); stale entries evicted so memory stays
  bounded; IPs held in memory only for the window, never persisted or logged
- Existing tests that assert the old `{"detail": ...}` shape are updated to
  the new shape. List every such test in the plan; no other changes to
  existing tests
- The 404 for unknown and malformed codes stays identical for both cases
  (no information leak), now in the new shape
- Route parameters use the `Annotated[...]` style
- No new dependencies

## Acceptance criteria
1. `GET /health` returns 200 and makes no DB call (verified with a failing DB
   dependency override).
2. `GET /ready` returns 200 with a working DB, and 503 in the standard error
   shape when the DB is unreachable, with no exception text in the body.
3. Every error listed under T-05.2 returns the standard shape with the right
   status and a stable `code` value; one test per case.
4. An unhandled exception (injected in a test) returns 500 with a generic
   message; the traceback is logged (asserted via caplog) and absent from
   the response body.
5. Validation errors include `details` with field location and message, and
   do not echo the submitted input.
6. Rate limit: with a limit of N, requests 1..N to POST succeed and request N+1
   returns 429 with `Retry-After`; after the window passes (injected clock),
   requests succeed again. Different client IPs have independent limits.
7. Rate limit does not apply to `GET /{code}`, the details endpoint, `/health`
   or `/ready` (more than N requests each, all succeed).
8. Limiter memory is bounded: entries for clients idle beyond the window are
   evicted (unit test on the limiter).
9. `/health`, `/ready`, `/docs` and `/openapi.json` are not captured by
   `/{code}`.
10. Latency test: p95 of redirect requests < 50 ms, measured with
    `time.perf_counter` after warm-up; runs as part of the normal test suite.
11. Unit tests (limiter, error mapping) and integration tests (all endpoints),
    including the failure cases above.
