# T-06: Click analytics and one defect fix (brownfield)

## Intent
Add click recording and per-link stats to the existing, tagged service
(baseline-greenfield) without changing existing behaviour or slowing
redirects, and fix one real defect in existing code, test-first.

## Context
- Baseline: tag baseline-greenfield (end of T-05b). All existing tests must
  keep passing unchanged.
- Requirements: FR-5 (record each redirect as a click), FR-6 (stats per
  link: total clicks, clicks per day, top referrers), Privacy (no raw IP
  addresses stored; analytics are aggregate only), Performance (analytics
  must never slow a redirect)
- ADR-001 D4: clicks recorded in a background task after the response is
  sent; a click may be lost on a crash (accepted: analytics, not critical)
- Q-3: total clicks only; unique visitors deferred (privacy)
- Plan: docs/plan.md T-06

## Scope
Phase A: defect (do first, on the baseline code)
- Review the existing code and report up to 3 candidate defects: real
  behaviour that contradicts requirements.md, an ADR or a brief, with
  evidence. Not style issues, not known limitations already recorded.
- STOP. I choose one.
- Test-first: write a test that reproduces the chosen defect, run it and
  show it failing (red), then fix it and show it passing (green).

Phase B: analytics (plan, then STOP for approval)
- Click model and Alembic migration: link reference, clicked_at (UTC),
  referrer host. No IP address, no user agent, no full referrer URL
- Recording: on a successful redirect only (302), via FastAPI
  BackgroundTasks, after the response
- GET /api/v1/links/{code}/stats →
  {"code", "total_clicks", "clicks_per_day": [{"date", "count"}],
  "top_referrers": [{"referrer", "count"}]}

Out of scope:
- Unique visitors, geography, device or browser stats
- Expiry (T-07)
- Message queue for click recording (ADR-001 D4's production path)

## Constraints
- Existing tests: no assertion changes. The only test changes allowed are
  in the defect's own test file, if the defect requires it (explain why)
- Background task opens its own DB session from the session factory. It
  must not reuse the request's session, which is closed before background
  tasks run
- A failure while recording a click is logged (without IP or referrer
  details) and never affects the redirect response
- Referrer: store only the lowercase host of the Referer header; a missing
  or unparseable header is counted as "(direct)"
- Stats computed with aggregate queries in the database (GROUP BY), not by
  loading click rows into Python; index to support per-link, per-day queries
- clicks_per_day: UTC dates, last 30 days, days with zero clicks omitted,
  sorted ascending. top_referrers: top 5 by count
- Stats for unknown or malformed codes: 404, identical to the details endpoint
- Migration: upgrade and downgrade work on SQLite and Postgres
  (render_as_batch is already set up); existing link data is untouched
- Route parameters use Annotated; no new dependencies; error shape per T-05

## Acceptance criteria
1. Phase A: the defect test fails on the baseline code and passes after the
   fix; both runs recorded.
2. Each 302 redirect records exactly one click; 404s record none.
3. The redirect response is sent before the click is written (test that the
   background task runs after the response), and a click-recording failure
   still yields a normal 302 (injected failure).
4. The click table contains no IP address, user agent or full referrer
   URL: schema test plus a round-trip test with a Referer carrying a path
   and query string.
5. Stats return correct total, per-day and top-referrer values for seeded
   clicks across multiple days and referrers, including "(direct)".
6. Stats for an unknown or malformed code return 404 in the standard shape.
7. Migration upgrade and downgrade pass on SQLite and Postgres, and
   existing links survive the upgrade.
8. All pre-existing tests pass unchanged, and the latency test still meets
   p95 < 50 ms with click recording active.
9. Unit and integration tests for the above.
