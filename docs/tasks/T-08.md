# T-08: Documentation (release)

## Intent
Give a reviewer everything needed to run, understand and evaluate the
project: an updated README, an architecture overview, and a final
engineering summary.

## Context
- Sources of truth: docs/requirements.md, docs/plan.md, docs/adr/*,
  docs/tasks/*, AI_LOG.md, the code, and current test results
- Requirement: runnable end-to-end by a reviewer from the README alone

## Scope
1. README.md (update)
   - Purpose (2–3 sentences); quick start (the verified fresh-clone steps,
     unchanged unless wrong); configuration (env vars per .env.example)
   - API: every endpoint with a curl example (create with and without
     expires_at, redirect, details, stats, health, ready) and the error shape
   - Running tests and scripts/check.py; project structure
   - Docs index linking requirements, plan, ADRs, task briefs,
     architecture, engineering summary, AI_LOG and transcripts
   - Known limitations (keep the existing list; add T-06/T-07 ones)

2. docs/architecture.md (new)
   - Component diagram (Mermaid): routers → services → repositories → DB,
     with background click recording and the error handlers
   - Data model: links and clicks (Mermaid ER), including expires_at, FK
     with cascade, and indexes
   - Sequence diagrams (Mermaid) for create and redirect (including the
     expired → 410 path and the background click write)
   - Cross-cutting: error shape, rate limiting, health vs ready, UTC
     handling, configuration
   - Key decisions: one line each, linking ADR-001 and ADR-002
   - Testing strategy and CI (SQLite locally, Postgres in CI)

3. docs/engineering-summary.md (new, at most about 3 pages)
   - Objective and what was delivered, per scenario: greenfield
     (T-01–T-05b), brownfield (T-06), ambiguous (T-07)
   - Approach: spec-first workflow (brief → plan → review → implement →
     verify → log), tools and their roles (Claude Code implements; Claude
     chat reviews plans and drafts options; I decide and verify), and
     manual vs auto mode, as stated in AI_LOG
   - Traceability: every FR and NFR → task → evidence (test files or checks)
   - Key decisions and trade-offs; assumptions (A-1 to A-4)
   - Risks and mitigations
   - Quality evidence: current test count, coverage and latency p95 from a
     fresh check.py run; CI setup
   - AI oversight: 5–7 notable cases from AI_LOG where AI output was
     corrected, rejected or verified, each citing its AI_LOG entry
   - Limitations and production next steps
   - Time spent: leave a TODO(Jaggu) marker; I'll fill it in

## Constraints
- Facts only from the repo. Don't invent metrics, decisions or history.
  Where something is unknown, write TODO(Jaggu) rather than guessing
- Attribution must match AI_LOG exactly (who raised what, what was
  accepted, edited or rejected)
- Mermaid diagrams must render on GitHub
- No code changes. Don't edit AI_LOG.md or transcripts
- If anything in the sources is contradictory, stop and ask

## Acceptance criteria
1. README quick start matches the verified clean-clone steps.
2. Every FR (1–7) and NFR appears in the traceability table with evidence.
3. Both ADRs linked; every link in the three documents resolves.
4. Metrics match a check.py run made during this task.
5. No claim in the summary lacks a source in the repo; TODO(Jaggu)
   markers only where I must supply information.

## Definition of done
Per docs/plan.md.
