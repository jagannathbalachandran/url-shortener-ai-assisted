  Candidate defect: validate_url accepts URLs with no real host

  What the code does — src/shortener/validation.py:26:
  if parsed.scheme.lower() not in ALLOWED_URL_SCHEMES or not parsed.netloc:
      raise InvalidUrlError(url)
  This only checks that urlsplit(url).netloc is a non-empty string. But netloc
  can be non-empty while there's no actual host — e.g. it's just a port (":80"),
  just userinfo ("@", "user:pass@"), or both — cases where
  urlsplit(url).hostname is None.

  What the spec says it should do — docs/plan.md (T-03 breakdown): "well-formed
  URL with a real host; max 2,048 characters." docs/tasks/T-03.md acceptance
  criterion 3: "Rejected with 422: javascript:, data:, file:, ftp: schemes;
  missing host; empty or malformed input; URLs over 2,048 chars." The existing
  test suite (tests/test_validation.py::MALFORMED_URLS) only tests the
  fully-empty-netloc case ("http://"), a narrower condition than "real host."

  Reproduce:
  from shortener.validation import validate_url
  validate_url("http://:80/path")         # ACCEPTED — no host at all
  validate_url("http://@/path")           # ACCEPTED
  validate_url("http://user:pass@/path")  # ACCEPTED
  I confirmed this end-to-end through the live app too: POST /api/v1/links 
  {"url": "http://:80/looks-like-a-path-not-a-host"} returns 201, and the
  resulting short code's redirect returns 302 with Location: 
  http://:80/looks-like-a-path-not-a-host.

  Impact — A short link can be created and will "successfully" redirect to a URL
  that has no host at all — it can never actually resolve anywhere. This is a
  direct miss of T-03's explicit "missing host → 422" acceptance criterion, and
  (more speculatively) userinfo-only/port-only netloc strings are exactly the
  kind of malformed-URL shape that has historically confused downstream
  URL/header parsers.

  This is a real, reproducible, spec-contradicting defect with a clear fix path
  (check parsed.hostname, not just parsed.netloc). Let me know if you'd like me
  to proceed with the test-first fix for this one.

  4. Stats: repository, service, schema

  src/shortener/repository.py — add ClickRepository (same file as
  LinkRepository, same convention as the existing free-standing ping_database):
  - add(click: Click) -> Click
  - total_clicks(link_id: int) -> int —
    select(func.count()).select_from(Click).where(...)
  - clicks_per_day(link_id: int, since: datetime) -> list[tuple[date, int]] —
    select(func.date(Click.clicked_at, type_=Date).label("day"), 
    func.count()).where(link_id=..., clicked_at >= 
    since).group_by("day").order_by("day"). func.date(...) is valid SQL on both

    datetime.date on both dialects (SQLite's date() returns text, Postgres'
    returns a native date — the explicit type makes both come back the same
    way).
  - top_referrers(link_id: int, limit: int) -> list[tuple[str, int]] — GROUP BY 
    referrer_host ORDER BY count DESC, referrer_host ASC LIMIT :limit (the
    referrer_host ASC tiebreaker is my own addition purely for deterministic
    output/tests — brief doesn't specify tie order).
